# 产物规格元模型

版本：`1.0.0`

## 1. 目的

本模型把《归云录：江岸危局》的设计、内容、工程、视觉和质量证据整理成可由 AI Agent 选择、生产、集成与验收的合同。规格描述目标，运行时代码描述现状；两者冲突时必须登记差异，不能静默修改规格迎合实现。

```text
产物类型 Product Type
└─ 产物子类型 Product Subtype
   ├─ 产物基础规格 Base Specification
   └─ 具体产物规格 Concrete Specification
```

| 层级 | 回答的问题 | 稳定性 | 《归云录》示例 |
| --- | --- | --- | --- |
| 产物类型 | 由哪条生产线负责？ | 跨项目稳定 | 视觉资源 |
| 产物子类型 | 生产什么形态？ | 同类项目稳定 | 可平铺场景纹理 |
| 产物基础规格 | 同类产物必须遵守什么？ | 可版本化复用 | 2 的幂尺寸、无文字、游戏内验收 |
| 具体产物规格 | 本项目实际交付什么？ | 随项目变化 | `assets/textures/bluestone-512.jpg`，512×512 JPEG |

基础规格可以被同类型项目复用；具体规格中的世界名、角色名、ID、数值、路径和证据只属于《归云录》，迁移到新项目时必须重新批准。

## 2. 强制字段

每个产物条目必须显式写出以下字段。未知项填写 `待决策`，同时指定责任 Agent 和阻塞范围；禁止使用“适当”“高质量”“参考现有”等不可验收描述。

| 字段组 | 必填字段 | 说明 |
| --- | --- | --- |
| 分类 | 目录 ID、基础规格 ID、具体规格 ID、类型、子类型 | 具体规格 ID 在库内唯一 |
| 基础规格 | 目的、输入契约、输出契约、不变量、命名规则、依赖、基础验收 | 描述同类产物的稳定合同 |
| 具体规格 | 实例 ID、精确参数、目标路径、消费方、完成条件、证据路径 | 描述本次可复现交付 |
| 治理 | 版本、状态、责任 Agent、变更原因、偏差 | 支持批次、回归和追踪 |

允许的产物状态：

```text
draft → approved → in_production → verified → deprecated
                     └─ blocked
```

- `draft`：字段可继续编辑，不允许进入生产。
- `approved`：具体规格已批准，可以创建工作单。
- `in_production`：工作单正在执行。
- `blocked`：缺少输入、权限或关键决策，必须记录责任方。
- `verified`：所需质量门和消费场景证据全部通过。
- `deprecated`：保留追溯，不再用于新批次。

## 3. ID 与命名

| 前缀 | 产物类型 |
| --- | --- |
| `DSN` | 游戏设计与内容 |
| `ENG` | 工程实现与配置 |
| `VIS` | 视觉、UI 与表现资源 |
| `QA` | 验证、证据与发布 |
| `OPS` | Agent、工作流与治理 |

基础规格 ID 格式：

```text
<TYPE>.<SUBTYPE...>
```

具体规格 ID 格式：

```text
<BASE_SPEC_ID>.<INSTANCE>
```

示例：

```text
VIS.TEXTURE.TILEABLE
VIS.TEXTURE.TILEABLE.GUIYUN_BLUESTONE
ENG.RUNTIME.STATIC_WEB.GUIYUN
QA.BROWSER.FULL_FLOW.GUIYUN
```

规则：

- 规格 ID 只使用大写 ASCII、数字和下划线，以 `.` 分段。
- 项目实例统一使用 `GUIYUN` 或 `GUIYUN_*` 结尾，避免与基础规格混淆。
- 代码资源键和数据 ID 使用小写 `snake_case`；文件名遵循现有项目约定，可使用 `kebab-case`。
- 各文档中的 `DC-01`、`E-01`、`V-01`、`Q-01` 是目录短编号，不能替代全局具体规格 ID。
- 已发布的规格 ID 不得改名；需要替代时新建 ID，并把旧条目标记为 `deprecated`。

## 4. 基础规格写法

基础规格必须独立回答：

1. 该产物由哪个运行时、Agent 或下游产物消费？
2. 上游输入必须具备哪些字段、状态和版本？
3. 输出是文档、JavaScript、CSS、图像、测试还是报告？
4. 哪些行为、接口、视觉或安全约束不可协商？
5. 哪些项目可以通过确定性命令检查？
6. 哪些体验必须在真实浏览器和目标视口中验收？

基础规格不得包含只属于《归云录》的角色名、任务文案、坐标和战斗数值；这些内容只能写入具体规格。

## 5. 具体规格写法

具体规格必须完全实例化基础规格：

- 给出准确的阶段键、角色 ID、资源路径、脚本顺序和引用关系。
- 给出可测量的数量、尺寸、坐标、冷却、伤害、条件和视口。
- 每个输入能追溯到已批准规格或仓库文件。
- 每个完成条件关联命令、断言、浏览器状态、截图或评审记录。
- 多文件产物必须列出完整清单，或指向可解析注册表。
- 现有实现与目标规格之间的缺口必须写入偏差，不得把“代码存在”直接等同于 `verified`。

## 6. 继承与覆盖

1. 具体规格继承同一子类型的全部基础规格。
2. 具体规格可以收紧，不能静默放宽基础规格。
3. 例外必须包含偏差 ID、原因、影响、批准者、修复责任人与失效条件。
4. 阶段键、资源路径、输入动作、状态字段和公共 API 不得由生产 Agent 自行改名。
5. 上游规格变更后，按依赖图重验所有直接与间接消费方。
6. 共享文件同一批次只能有一个写入所有者；其他 Agent 通过变更请求交付。

## 7. 验收层级

| 级别 | 验收方式 | 典型产物 | 通过条件 |
| --- | --- | --- | --- |
| L0 结构 | 文件、命名、图像头、字段和引用静态检查 | 文档、图片、脚本、资源路径 | 可解析、字段完整、无悬空引用 |
| L1 逻辑 | 纯函数、状态机、数值和边界断言 | 任务、战斗、碰撞、恢复 | 输入输出与失败边界符合规格 |
| L2 集成 | 脚本语法、项目本地契约、静态启动 | 模块加载、资源接入、场景消费 | `file://` 与 HTTP 启动，无加载错误 |
| L3 体验 | 真实浏览器流程、视口矩阵和截图评审 | 移动、战斗、轻功、HUD、视觉 | 可通关、可读、无阻断错误 |

门禁要求：

- 所有运行时可见产物至少通过 L0、L2、L3。
- 纯逻辑产物至少通过 L0、L1、L2。
- 单张图像完成生成只算 L0；必须在最终材质、构图和目标视口中完成 L3。
- 自动化 debug 路径证明状态可达，不替代真实输入和人工体验验收。

## 8. 可追溯关系

```text
需求与概念参考
  → 设计具体规格
    → 内容 / 工程 / 视觉工作单
      → 数据、代码、图片与生成记录
        → index.html 脚本顺序和运行时消费
          → 项目本地检查与浏览器回归
            → 验收报告和发布提交
```

每个具体规格最少维护：

| 字段 | 示例 |
| --- | --- |
| `spec_id` | `VIS.TEXTURE.TILEABLE.GUIYUN_BLUESTONE` |
| `depends_on` | `VIS.STYLE.GUIDE.GUIYUN` |
| `outputs` | `assets/textures/bluestone-512.jpg` |
| `consumed_by` | `src/materials.js`、`src/world.js` |
| `verified_by` | 图像头检查、材质状态、山门/寺院截图 |

## 9. 变更影响等级

| 等级 | 示例 | 最低重验 |
| --- | --- | --- |
| 局部 | 一句不影响条件的提示文案 | 直接消费 UI 的 L0/L3 |
| 域内 | 一项技能数值、一个纹理或一种敌人行为 | 该域 L0-L3 与相邻路径 |
| 跨域 | 阶段键、角色 ID、资源路径、输入映射 | 所有直接/间接消费方 L0-L3 |
| 发布级 | 脚本顺序、Three.js 版本、启动协议 | 全量静态、桌面、手机与发布回归 |

## 10. 完成定义

产物只有同时满足以下条件才能标记为 `verified`：

- 输出存在，并与具体规格逐项一致。
- 上游依赖处于 `approved` 或 `verified`。
- 必需的 L0-L3 质量门全部通过。
- 真实消费方成功读取路径、ID、字段或资源。
- 失败、恢复、重试和移动端边界按风险覆盖。
- 验收证据包含版本或提交，可从规格定位输出，也可从输出反查规格。
- 所有偏差已关闭，或由明确责任人限期接受。
