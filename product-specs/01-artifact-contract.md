# 产物合同模型

## 1. 四层结构

每项产物使用同一结构：

```text
产物类型 → 产物子类型 → 基础规格 → 项目具体规格
```

| 层级 | 回答的问题 | 是否可直接复用 |
| --- | --- | --- |
| 产物类型 | 由哪条生产线负责 | 是 |
| 产物子类型 | 交付什么形态 | 是 |
| 基础规格 | 同类产物必须满足什么合同 | 是 |
| 项目具体规格 | 本项目交付哪些 ID、参数、路径和证据 | 否，必须重新实例化 |

基础规格不得包含项目名称、角色、任务文案、坐标、伤害值、框架版本或发布地址。具体规格必须把这些字段填写完整。

## 2. 基础产物目录

| 基础规格 ID | 类型 | 子类型 | 主要输出 | 主要消费方 |
| --- | --- | --- | --- | --- |
| `PRJ.PROFILE` | 项目治理 | 项目画像 | 平台、闭环、边界、能力与证据要求 | 全部 Agent |
| `DSN.SLICE` | 设计 | 竖切总纲 | 核心体验、时长、黄金路径、完成条件 | 内容、工程、QA |
| `DSN.FLOW` | 设计 | 状态与内容流程 | 状态、触发、目标、失败和恢复 | 运行时、UI、QA |
| `DSN.SYSTEM` | 设计 | 玩法系统 | 输入、规则、数值、AI、反馈 | 工程、视觉、QA |
| `ENG.RUNTIME` | 工程 | 可执行运行时 | 入口、模块、数据、资源和调试接口 | 浏览器或目标运行环境 |
| `VIS.PACK` | 视觉 | 视觉资源包 | 风格、图像、模型、材质、VFX、UI | 运行时和玩家 |
| `QA.PLAN` | 质量 | 验收计划 | 场景矩阵、断言、环境和门禁 | QA Agent |
| `QA.EVIDENCE` | 质量 | 验收证据 | 命令、状态、截图、错误和网络记录 | 发布与审计 |
| `OPS.RELEASE` | 运营 | 发布包 | 提交、构建、地址、回滚点和发布结论 | 玩家与后续批次 |
| `OPS.DECISION` | 治理 | 决策与偏差 | 决策、偏差、责任人和失效条件 | 全部受影响产物 |

新类型只有在现有条目无法表达真实消费方时才增加。不要为每个文件创建一个类型。

## 3. 具体规格 ID

格式：

```text
<BASE_SPEC_ID>.<PROJECT_ID>.<ARTIFACT_ID>
```

示例：

```text
DSN.FLOW.PROJECT_A.MAIN_QUEST
VIS.PACK.PROJECT_A.WORLD_TEXTURES
QA.EVIDENCE.PROJECT_A.RELEASE_003
```

规则：

- 只使用大写 ASCII、数字和下划线，以 `.` 分段。
- `PROJECT_ID` 在项目画像中冻结。
- 已进入 `approved` 的 ID 不得改名；替代时创建新 ID 并弃用旧项。
- 运行时 ID、资源键和文件名可以遵循项目原有规范，但必须在具体规格中建立映射。

## 4. 强制字段

每个具体规格必须填写：

| 字段组 | 必填字段 |
| --- | --- |
| 身份 | `spec_id`、`base_spec`、版本、状态、责任 Agent |
| 目标 | 目的、玩家或业务价值、非目标 |
| 输入 | 上游规格、现有文件、数据、参考、权限 |
| 输出 | 精确路径、格式、数量、字段、参数 |
| 消费 | 消费方、加载方式、调用或引用位置 |
| 不变量 | 不得破坏的 ID、顺序、协议、体验与安全边界 |
| 验收 | 所需 L0–L3、断言、环境、视口、正向与失败场景 |
| 证据 | 命令、提交、状态、截图、错误、网络、评审记录 |
| 治理 | 变更原因、偏差、回滚点、影响范围 |

未知字段写 `BLOCKED:<原因>`，同时指定责任人。禁止使用“适当”“高质量”“参考现有”作为完成条件。

## 5. 状态

```text
draft → approved → in_production → verified → deprecated
                     └─ blocked
```

- `draft`：可编辑，不可直接下发生产。
- `approved`：字段和边界已确认，可创建工作单。
- `in_production`：工作单正在执行。
- `blocked`：缺输入、权限或关键决策。
- `verified`：真实消费方和所需门禁全部通过。
- `deprecated`：保留追溯，不再用于新批次。

“代码已经存在”不等于 `verified`；“图片生成成功”也不等于已接入。

## 6. 依赖与影响

每项具体规格至少维护：

```text
depends_on → outputs → consumed_by → verified_by
```

影响等级：

| 等级 | 典型变化 | 最低回归 |
| --- | --- | --- |
| 局部 | 不影响条件的文案或样式 | 直接消费方 |
| 域内 | 一项数值、一个资源、一种行为 | 本域与相邻路径 |
| 跨域 | 状态 ID、资源键、输入映射、公共字段 | 全部直接和间接消费方 |
| 发布级 | 入口、依赖版本、启动协议、存档或网络合同 | 全量 L0–L3 和发布门 |

## 7. 偏差

偏差必须包含：

- 偏差 ID 与发现版本。
- 预期和实际。
- 玩家或下游影响。
- 严重度与状态。
- 临时处理、责任人、批准者。
- 修复条件或永久接受理由。
- 需要重验的消费方。

偏差不能静默降低基础规格，也不能作为所有后续项目的默认例外。

## 8. 完成定义

产物只有同时满足以下条件才能标记 `verified`：

- 输出存在且与具体规格一致。
- 上游依赖处于 `approved` 或 `verified`。
- 真实消费方成功加载、调用或显示产物。
- 所需 L0–L3 全部通过。
- 正向、失败、恢复和目标平台边界按风险覆盖。
- 证据绑定提交或版本，可双向追溯。
- 偏差已经关闭，或由明确责任人批准并具备失效条件。
